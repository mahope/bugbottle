Bug reports that arrive with the evidence attached.

I kept getting emails that said “the save button does nothing” and not much else. This is the piece that attaches everything I would otherwise have had to ask for.

bugbottle collects what the browser already knows at the moment someone notices: the path, the viewport, the console errors from the last few minutes, the element they point at, and a screenshot if you turn that on. It POSTs the lot as JSON to a route you wrote. No dashboard, no account, nothing in the middle. Your reports never touch my servers, because there are none.

What it does, and what it leaves to you

You write the form
The library holds the state, collects the evidence and makes the request. It renders nothing unless you ask for the ready-made panel.
You own the endpoint
A report is a JSON body arriving at a route you wrote. There is nothing to sign up for. The validators that check what arrives ship in bugbottle/server.
It stays small
No runtime dependencies, and one entry point per piece, so a page pays only for what it imports. The core is 1.3 kB gzipped. The table below has the rest.
People can point
pickElement() returns a short CSS selector, the tag, the visible text and the position: enough for me, or for a coding agent, to open the right file rather than guess at it.
It speaks eight languages
Danish, English, Swedish, Norwegian, German, Dutch, French and Spanish, with every string replaceable and the panel themed from a handful of CSS variables.
The server side trusts nothing
Everything the browser sends is treated as hostile input: lengths clipped, null bytes stripped, and a screenshot checked by the signature in its decoded bytes rather than the type it claims to be.

Three ways to install it

All three post the same JSON to a route you write. Pick by what the project already has.

With a bundler

Install it, start recording console errors, mount the panel.

terminal
npm install bugbottle
main.js
import { initConsoleBuffer } from "bugbottle";
import { mountBugbottle } from "bugbottle/ui";

initConsoleBuffer();
mountBugbottle({ endpoint: "/api/feedback" });

One script tag

For a site with no build step: a WordPress theme, a static page, a client site somebody else deploys. It mounts itself from the data attributes.

There are two files. bugbottle.js carries everything; bugbottle.slim.js is the same panel in all eight languages without the annotator, the timings snapshot, shake-to-report and the network log, and says so on the console if you ask for one of them.

index.html
<script
  src="https://cdn.jsdelivr.net/npm/bugbottle@0.9.0/dist/bugbottle.js"
  data-endpoint="/api/feedback"
  data-brand="Acme"
></script>

WordPress

A plugin that mounts the same panel and keeps the reports in the installation itself: a private post type with an admin list, an optional email, Danish and English. One activation, no build step, no developer on call.

Download the plugin or read the settings first.

Open the panel and read what it would have sent

The button in the corner is the real bugbottle/ui panel, running from the same dist/ that npm ships. Open it, write a line, point at something on this page, press send.

There is no endpoint behind it. The demo hands the library a fetch of its own, keeps the body that would have been posted, and renders it here with toMarkdown from bugbottle/server, which is the same function you would use for an issue body. Screenshots are off here, since the demo has nowhere private to put one.

The report, as Markdown

toMarkdown(report)

Read this before you turn screenshots on

      

      

        

          A screenshot of your application contains whatever the reporter could see. In a
          clinical system that can mean a patient photograph; in a payroll tool, a salary;
          in yours, perhaps somebody's inbox or a half-written message they had not sent
          yet.
        

        
Three things follow, and the library cannot do them for you:

        
    
          
  1. 
            Put screenshots somewhere private. If your object storage
            bucket has a public read policy, and many media buckets do, anything you write
            to it can be fetched by anyone holding the URL. Use a separate bucket with no
            public policy.
          
    2. 
          
  2. 
            Serve them back through an authenticated route. Never give a
            screenshot a public URL. Look the storage key up from the row rather than
            taking it from the request, so an id cannot be used to walk your bucket.
          
    3. 
          
  3. 
            Say so before the picture is taken. Put it in the form, next
            to the checkbox, not in a policy nobody opens.
          
    4. 
        

        

          Requiring people to be signed in is worth considering too. An anonymous
          screenshot is one nobody can be asked about later, and nobody can be told has
          been deleted.
          The full section in the README.
